# Relatório de Auditoria RAG & Google Drive Integration - TheoSphere

**Data:** 2026-05-22  
**Auditor:** SDET Sênior & Especialista em Avaliação de RAG/LLMs  
**Status do Pipeline:** 🔴 ALTO RISCO (High Risk) devido a vulnerabilidades de sincronização, exaustão de recursos e chunking impróprio.

---

## 1. 📊 Sumário Executivo (Executive Summary)

A avaliação programática do pipeline de ingestão do Google Drive e do sistema RAG (Retrieval-Augmented Generation) da TheoSphere revelou conformidades robustas em termos de isolamento de dados no banco vetorial via Prisma/pgvector. No entanto, foram encontradas **três vulnerabilidades críticas** de engenharia de software e arquitetura de RAG que comprometem a resiliência operacional, a segurança contra DoW (Denial of Wallet) e a fidelidade da exegese teológica.

### Classificação de Risco Geral: 🔴 CRÍTICO / ALTO (High Risk)

- **Segurança & Resiliência:** Alta exposição a Denial of Wallet (DoW) e esgotamento de memória no worker Node.js (CWE-400).
- **Consistência de Dados:** Sincronização inadequada que resulta em dados órfãos e obsoletos (CWE-662).
- **Fidelidade Exegética (Qualidade do RAG):** Fragmentação conceitual severa devido ao chunking arbitrário de referências bíblicas e textos teológicos estruturados.

### Falha 1: Ingestão de Arquivo Sem Limite de Tamanho & Buffer In-Memory

- **Componente:** [text-extractors.ts](file:///Users/cristianocolombo/Downloads/TheoSphere/backend/src/rag/text-extractors.ts#L115-L188) & [drive-rag.service.ts](file:///Users/cristianocolombo/Downloads/TheoSphere/backend/src/rag/drive-rag.service.ts#L154-L161)
- **Gravidade:** 🔴 Alta (High)
- **CWE:** **CWE-400: Uncontrolled Resource Consumption** (Exaustão de Memória / Disco)
- **Descrição:** O arquivo do Drive é baixado inteiro para a memória (`Buffer.from(response.data)`) e o extrator EPUB grava o buffer em `/tmp` sem validar o tamanho máximo. Um arquivo de 5GB causará estouro de pilha/heap no Node.js (OOM Crash) ou esgotará o espaço em disco do servidor temporário.
- **Snippet de Correção (`text-extractors.ts`):**

  ```typescript
  // Adicionar validação de tamanho máximo (ex: 100MB) antes de ler o buffer
  const MAX_FILE_SIZE_BYTES = 100 * 1024 * 1024; // 100MB

  // Na chamada drive.files.get, ler o header Content-Length primeiro
  const metadata = await drive.files.get({ fileId: file.id, fields: "size" });
  const fileSize = parseInt(metadata.data.size || "0", 10);
  if (fileSize > MAX_FILE_SIZE_BYTES) {
    throw new Error(
      `File is too large (${(fileSize / 1024 / 1024).toFixed(2)}MB). Max allowed is 100MB.`,
    );
  }
  ```

### Falha 2: Sincronização de Estado Ignora Mutações (Stale Data)

- **Componente:** [drive-rag.service.ts](file:///Users/cristianocolombo/Downloads/TheoSphere/backend/src/rag/drive-rag.service.ts#L132-L146)
- **Gravidade:** 🔴 Alta (High)
- **CWE:** **CWE-662: Improper Synchronization** (Dessincronização de Estado)
- **Descrição:** Quando um arquivo mutaciona no Google Drive, o webhook dispara a sincronização. Contudo, o método `processFile` apenas checa se o `fileId` já existe na tabela `UserEmbedding` e, se sim, **pula o processamento** (`return`). Isso deixa o banco vetorial permanentemente desatualizado em relação a alterações diretas nos arquivos teológicos do Drive.
- **Snippet de Correção (`drive-rag.service.ts`):**

  ```typescript
  // Obter o modifiedTime do arquivo através da API do Google Drive
  const driveFile = await drive.files.get({
    fileId: file.id,
    fields: "modifiedTime",
  });
  const driveModifiedTime = new Date(driveFile.data.modifiedTime).getTime();

  // Buscar no banco vetorial o último timestamp de indexação do arquivo
  const lastIndexed: any[] = await this.prisma.$queryRaw`
    SELECT (metadata->>'lastModified')::bigint as last_mod
    FROM "UserEmbedding"
    WHERE "userId" = ${targetUserId} AND metadata->>'fileId' = ${file.id}
    LIMIT 1
  `;

  if (lastIndexed.length > 0 && lastIndexed[0].last_mod >= driveModifiedTime) {
    this.logger.log(
      `Arquivo "${file.name}" já está atualizado no RAG. Pulando...`,
    );
    return;
  }

  // Se mudou, removemos os chunks antigos antes de re-ingerir (DELETE -> INSERT)
  if (lastIndexed.length > 0) {
    this.logger.log(
      `Arquivo "${file.name}" mutou no Drive. Removendo chunks obsoletos...`,
    );
    await this.prisma.userEmbedding.deleteMany({
      where: {
        userId: targetUserId,
        type: "library_book",
        metadata: { path: ["fileId"], equals: file.id },
      },
    });
  }
  ```

### Falha 3: Chunking Baseado em Caracteres Semânticos Quebra Sentenças Teológicas

- **Componente:** [drive-rag.service.ts:chunkText](file:///Users/cristianocolombo/Downloads/TheoSphere/backend/src/rag/drive-rag.service.ts#L248-L273)
- **Gravidade:** 🟡 Média (Medium)
- **CWE:** N/A (Falha Algorítmica de Precisão)
- **Descrição:** O fatiador de textos divide o texto por parágrafos duplos `\n\s*\n` e acumula caracteres até alcançar 1000. Isso quebra referências exegéticas, comentários e versículos de forma arbitrária. Em teologia computacional, cortar a sentença no meio (ex: separar a premissa grega de sua conclusão exegética) induz o LLM ao erro/alucinação.
- **Snippet de Correção (Adotando Chunking Teológico por Sentença/Parágrafo Bíblico):**

  ```typescript
  // Substituir chunkText por um fatiador semântico baseado em limites lógicos/frases
  private chunkTextSemantico(text: string, maxTokens: number = 400): string[] {
    // Divide por sentenças completas que terminam com (. ! ?) seguidos de espaço,
    // ou limites óbvios de versículos (ex: João 3:16)
    const sentences = text.match(/[^.!?]+[.!?]+(\s|$)|.+/g) || [text];
    const chunks: string[] = [];
    let currentChunk = "";

    for (const sentence of sentences) {
      if ((currentChunk + sentence).length > maxTokens * 4) { // Estimativa de tokens
        chunks.push(currentChunk.trim());
        currentChunk = sentence;
      } else {
        currentChunk += sentence;
      }
    }
    if (currentChunk.trim()) chunks.push(currentChunk.trim());
    return chunks;
  }
  ```

### Falha 4: Vulnerabilidade a Denial of Wallet (DoW) no Gateway RAG

- **Componente:** [rag.service.ts](file:///Users/cristianocolombo/Downloads/TheoSphere/backend/src/rag/rag.service.ts)
- **Gravidade:** 🔴 Alta (High)
- **CWE:** **CWE-400: Denial of Wallet (DoW) via Context Inflation**
- **Descrição:** A API de busca vetorial aceita queries de qualquer tamanho e as encaminha diretamente para o LLM. Um atacante pode enviar prompts gigantescos (ex: 50.000 tokens de spam repetitivo), inflando drasticamente a fatura de chamadas à API da Google/Gemini.
- **Snippet de Correção (Validação no Gateway):**
  ```typescript
  // Injetar validação robusta de tamanho de caracteres no DTO ou no Service
  if (query.length > 3000) {
    throw new BadRequestException(
      "A sua pergunta teológica excede o limite máximo permitido de 3000 caracteres.",
    );
  }
  ```

## 4. 🏛️ Recomendação de Arquitetura (Architecture Recommendation)

### Avaliação da Estratégia de Embedding: OpenAI `text-embedding-ada-002` / Gemini Embeddings vs. Modelo Fine-Tunado Especializado

Atualmente, o projeto utiliza chamadas para o modelo padrão da Gemini / OpenAI.

#### Por que modelos de prateleira falham no domínio Bíblico/Teológico?

1.  **Vocabulário Multilíngue Complexo:** Textos teológicos avançados usam termos transliterados e caracteres reais em Grego Koiné (ex: `dikaiosyne`, `charis`), Hebraico Bíblico (ex: `hesed`, `’elohim`) e Latim Patrístico. Modelos como `ada-002` têm baixa densidade vetorial e representação subotimizada para essas línguas antigas.
2.  **Alta Densidade Conceitual:** Sentenças curtas como "O Verbo se fez carne" (João 1:14) carregam uma densidade semântica maciça (Doutrina da Encarnação) que modelos gerais atenuam como apenas "comida e carne física".

#### Tabela Comparativa de Estratégias

| Dimensão                   | Modelo de Prateleira (ex: Ada-002 / Gemini standard)            | Modelo Open-Source Fine-Tunado (ex: BGE-M3 / Stella)      |
| :------------------------- | :-------------------------------------------------------------- | :-------------------------------------------------------- |
| **Precisão Exegética**     | 🟡 Média. Ignora nuances linguísticas antigas (Grego/Hebraico). | 🟢 Excelente. Captura semântica fina de Strong e lemas.   |
| **Custo de Token**         | 🔴 Recorrente (Cobrado por API call).                           | 🟢 Zero (Self-hosted em VPS barata ou Cloudflare Worker). |
| **Performance (Latência)** | 🟡 Depende da rede externa.                                     | 🟢 Sub-15ms se rodando local/borda em GPU/CPU otimizada.  |
| **Recomendação**           | **Usar apenas como baseline de desenvolvimento.**               | **RECOMENDADO para produção (Fase Final).**               |

### Proposta de Nova Topologia RAG

1.  **Modelo de Embedding:** Migrar para o **BGE-M3** (modelo de embedding multilíngue de alta performance) e realizar **Fine-Tuning sintético** usando o parágrafo bíblico + Dicionários Teológicos (BDAG/HALOT) como dataset de âncora e contraste.
2.  **Estratégia de Ingestão:** Implementar **Parent-Child Chunking**:
    - **Child Chunks (200 tokens):** Guardados para busca vetorial ágil de alta precisão (cosseno).
    - **Parent Chunks (1000 tokens / capítulo/parágrafo completo):** Enviados ao LLM para síntese contextualmente rica, garantindo zero fragmentação e fidelidade hermenêutica absoluta.

## 🔴 Bloqueador encontrado no deploy: a IA não está respondendo em produção

O deploy resolveu o que era código. Sobrou um problema de **configuração**, que só aparece testando produção de verdade.

### Evidência

Pedido de dossiê Factbook sobre **Nínive**, em produção:

```
{"verse":"Gênesis 1:1","original_language":"HB","interlinear":[{"word":"בְּרֵאשִׁית"...
```

Pergunta simples, em texto, sobre **Nínive**:

```
## Análise Teológica
Essa é uma questão fundamental na teologia cristã...
### 📖 Perspectiva Reformada ... ### 📖 Perspectiva Arminiana ...
```

Nenhuma das duas tem relação com a pergunta. `cached: false` nos dois casos — não é o cache semântico.

### Causa

Ambas as respostas vêm de `backend/src/rag/fallback-responses.ts`, o texto enlatado que o `rag.service` devolve quando a chamada à IA não produz conteúdo (`rag.service.ts:558`). O construtor do serviço (`rag.service.ts:73-86`) decide o provedor assim:

```ts
if (geminiKey && geminiKey !== 'your_gemini_api_key_here')   → Gemini
else if (openaiKey && !openaiKey.startsWith('sk-your'))      → OpenAI
else  logger.warn('Nenhuma API KEY configurada. Operando em modo Fallback Teológico.')
```

O `render.yaml` declara `GEMINI_API_KEY` com `sync: false` — ou seja, **o valor tem que ser preenchido à mão no dashboard do Render**. Os sintomas dizem que ele está ausente, inválido ou com a cota esgotada.

### Por que isso passou despercebido até agora

O fallback devolve JSON bem formado e HTTP 200. Nenhum health check acusa. E até ontem o crash do Factbook mascarava o problema; depois dele, a recusa de domínio mascarava; agora que os dois sumiram, o que aparece é este.

### O que fazer

1. Dashboard do Render → serviço do backend → **Environment**
2. Conferir `GEMINI_API_KEY` (ou `OPENAI_API_KEY`): existe? é válida? tem cota?
3. Salvar dispara redeploy automático
4. Validar com:
   ```bash
   curl -s -X POST https://theosphere.onrender.com/api/v1/rag/chat \
     -H 'Content-Type: application/json' \
     -d '{"query":"Quem foi Ninive na Biblia? Responda em duas frases."}' | head -c 300
   ```
   Resposta correta fala de Nínive. Se vier "Perspectiva Reformada / Arminiana", a chave continua sem funcionar.

Nos logs do Render, procure na inicialização por `Nenhuma API KEY (Gemini/OpenAI) configurada` — é a confirmação definitiva.

## Duas descobertas de infraestrutura

**1. O link da Vercel estava quebrado.** `frontend-v2/.vercel/project.json` apontava para um `projectId` que a CLI recusava ("projeto deletado, transferido ou sem acesso"). Refiz o link para o projeto `frontend-v2` existente. Backup do arquivo antigo em `/tmp/vercel_project_backup.json`.

**2. A raiz do monorepo está publicando lixo.** Existe um projeto Vercel chamado `cristianocolombo` conectado ao Git e apontando para a **raiz** do repositório. O push de hoje o disparou e ele publicou uma única função `index` de 2.89MB — não o app (o app real tem 157 saídas). É exatamente o cenário contra o qual o `DEPLOY.md` alerta: o `package.json` da raiz existe só para husky/lint-staged e não é deployável.

Ele responde em `cristianocolombo.vercel.app`. Vale decidir: apagar o projeto, ou apontar o Root Directory dele para `frontend-v2`. Do jeito que está, cada push gera um deploy inútil — e existe o risco de alguém abrir a URL errada achando que é a plataforma.
